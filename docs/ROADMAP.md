# StardustFS 개발 로드맵

## 최종 목표

- 사용자는 StardustFS 웹 서비스에 가입하여야 함
- metadata_db와 key_file은 서버에 백업이 있음
- 여러 PC/Linux에서 같은 계정으로 다른 위치의 스토리지의 원격 파일을 접근 가능
- 다른 사용자의 스토리지에 리플리케이션을 암호화하여 저장 가능
- 서비스 제공자는 사용자 등급에 따라 리플리케이션 대상 파일 각각에 대한 정보를 중계/제어
- 리플리케이션은 최소 3세트의 백업이 온라인으로 존재하여야 함
- 사용자 간 파일 교환은 P2P 방식을 사용

## 개발 단계 개요

```
MVP1 (완료)              MVP2                    MVP3                    MVP4
로컬 암호화 WebDAV  →  멀티디바이스 동기화  →  리플리케이션 (P2P)  →  서비스 플랫폼
단일 PC, 로컬 전용       원격 스토리지 접근       암호화 백업 + 패리티     등급/과금/중계

MVP5 (폐기): 평문 사용자 간 공유 — 보안상 폐기, 교차 계정 P2P는 MVP3 암호화 복제로 단일화
```

## MVP1: 로컬 암호화 WebDAV (완료)

단일 PC에서 동작하는 암호화 가상 파일시스템.

- AES-256-GCM 파일 암호화
- JBOD 스토리지 통합 (Directory + Loopback)
- WebDAV 서버 (wsgidav/cheroot)
- SQLite 메타데이터
- HTTP Basic Auth

## MVP2: 멀티디바이스 + 서버 백업

사용자가 여러 PC/Linux에서 동일 계정으로 원격 스토리지에 접근.

핵심 기능:
- 사용자 계정 시스템 (가입/로그인/토큰 발급)
- 중앙 서버에 metadata_db + key_file 암호화 백업/동기화
- 원격 스토리지 소스 지원 (로컬 소스 외에 원격 HTTP/S3 소스 추가)
- 디바이스 등록: 같은 계정으로 여러 디바이스에서 접근
- 메타데이터 동기화: 디바이스 간 metadata_db 병합

아키텍처:
```
[PC-A StardustFS] ←→ [StardustFS 중앙 서버] ←→ [PC-B StardustFS]
                         ↓
                   metadata_db 백업
                   key_file 암호화 보관
                   디바이스 레지스트리
```

## MVP3: 리플리케이션 (P2P 백업)

다른 사용자의 스토리지에 암호화된 복제본을 저장.

핵심 기능:
- 리플리케이션 프로토콜: 파일 단위로 3개 이상의 원격 노드에 복제
- 암호화 복제: 복제본은 원본 소유자의 키로 암호화됨 (호스트가 내용을 볼 수 없음)
- 노드 디스커버리: 중앙 서버가 복제 대상 노드를 매칭
- 복제 상태 추적: 각 파일의 복제 수(replica count) 관리
- 복구 프로토콜: 소스 유실 시 복제본에서 자동 복원

아키텍처:
```
[사용자 A] ──암호화된 청크──→ [사용자 B 스토리지]
                            → [사용자 C 스토리지]
                            → [사용자 D 스토리지]
                                (최소 3세트)
```

## MVP4: 서비스 플랫폼

서비스 제공자가 등급별로 리플리케이션을 중계/제어.

핵심 기능:
- 사용자 등급 시스템 (Free / Pro / Enterprise)
- 등급별 제한: 복제 수, 총 용량, 전송 대역폭
- 과금 시스템: 스토리지 제공자에게 보상, 소비자에게 과금
- 관리자 대시보드: 노드 상태, 복제 건강도, 사용량 모니터링
- SLA 보장: 복제본 3세트 미만 시 자동 재복제 트리거

등급 예시:
| 등급 | 내 스토리지 | 리플리케이션 | 대역폭 |
|------|------------|-------------|--------|
| Free | 10GB | 1세트 (최소 보장 없음) | 1MB/s |
| Pro | 100GB | 3세트 (보장) | 10MB/s |
| Enterprise | 무제한 | 5세트 + 지역 분산 | 무제한 |

## MVP5: P2P 파일 교환 (폐기 — MVP3로 흡수)

> 결정(2026-05): "평문 사용자 간 파일 공유" 방향은 폐기한다.
> 교차 계정 P2P 전송은 보안상 암호화된 복제/패리티 청크에 한해서만 허용하며,
> 호스트(수신 계정)는 내용을 복호화할 수 없어야 한다. 즉 다른 계정과의 P2P
> 전송의 유일한 정당한 용도는 MVP3의 암호화 리플리케이션(백업 패리티 요청)이다.
> 평문 파일을 타 계정에 직접 건네는 Dropbox식 공유 링크는 구현하지 않는다.

폐기 근거:
- 최종 목표상 교차 계정 데이터는 항상 "원본 소유자 키로 암호화된 복제본"이어야 함
- 평문 공유를 허용하면 호스트가 타인 데이터를 열람 가능 → 보안 모델 위반
- 따라서 교차 계정 P2P = 암호문만, 항상 (MVP3로 단일화)

재활용:
- MVP5 데모에서 만든 share_token 인가 인프라(중앙 서버 /shares + P2PServer
  토큰 위임 검증 + 경로 격리)는 폐기하지 않고 MVP3의 "복제 노드 접근 인가"
  토대로 재사용한다. 단 MVP3에서는 접근 대상을 "복제 계약에 등록된 암호화
  청크"로 제한해야 하며, 임의 경로 공유는 허용하지 않는다.
- 관련 스펙: `.kiro/specs/mvp5-file-sharing-demo/` (PoC로 보존, MVP3에서 승계)


## 의존 관계

```
MVP1 → MVP2 → MVP3 → MVP4
                (MVP5 폐기: 교차 계정 P2P는 MVP3 암호화 복제로 단일화)
```

MVP2가 가장 중요한 전환점. 로컬 전용에서 네트워크 서비스로 전환되는 시점이고 이후 모든 기능의 기반.

MVP2 완료 후 다음 단계는 MVP3(암호화 리플리케이션)이다. MVP5 데모에서 검증한 교차 계정 토큰 인가 인프라를 MVP3의 복제 노드 접근 인가로 승계한다.
