# StardustFS 파일 저장 위치 정책

파일이 실제로 어디에 저장되는지를 예시로 설명한다. 서버는 어떤 경우에도 파일
내용을 저장하지 않는다(zero-knowledge).

핵심: 파일 실체(암호문)의 위치는 4단으로 결정된다.

1. 기본은 파일을 만든 기기의 로컬 스토리지
2. 로컬이 차면 내 다른 온라인 기기로 넘김(스필오버)
3. 백업 사본은 다른 기기에 암호문 조각으로 복제
4. 공간이 부족하면 로컬 원본을 비우고, 읽을 때 사본에서 복구(축출, 기본 꺼짐)

다른 기기는 "어디에 있는지"만 안다(메타데이터). 필요할 때 가져온다.

## 1단: 기본 배치 — 만든 기기

PC-A에서 파일 A를 만들면 암호문은 PC-A의 로컬 스토리지에 저장된다. 로컬 소스가
여러 개면 여유 공간이 가장 많은 소스를 고른다(원격 소스는 후보에서 제외).

- PC-B에는 "파일 A는 PC-A에 있다"는 메타데이터만 서버를 통해 전달된다.
- PC-B 화면에는 파일 A가 보이지만 실체는 없다.

```
파일 A 실체:  [PC-A ✅]   [PC-B ❌ 목록만 보임]
```

구현: `jbod_manager.write_file` → `select_source`(로컬 활성 소스 중 여유 최대)

## 2단: 스필오버 — 로컬이 차면 내 다른 기기

신규 파일을 저장할 때 로컬 소스가 모두 만석이면, 내 계정의 다른 온라인 기기로
암호문을 보내 저장하고 메타데이터를 그 기기 소유로 기록한다.

- 즉 PC-A에서 만든 파일이 PC-B에 저장될 수 있다.
- 도달 가능한 온라인 기기가 없으면 저장하지 않고 용량 부족 에러를 낸다(무손실,
  조용히 건너뛰지 않는다).
- 기존 파일 덮어쓰기에는 스필오버가 적용되지 않는다(원래 소스에 그대로 쓴다).

```
로컬 만석:  PC-A ──암호문──▶ [PC-B에 저장, 소유=PC-B]
도달 불가:  저장 실패 (InsufficientStorageError)
```

구현: `jbod_manager._write_to_remote`

## 3단: 백업 사본 — 다른 기기에 암호문 조각으로

데몬이 파일을 암호문 청크로 나눠 다른 기기에 복제한다. 기본으로 켜져 있다
(`replication.enabled`, 기본 true). 복제가 시작되는 시점은 세 가지다.

- 파일을 저장하면 즉시(데몬이 전송을 마친 직후 스스로 알림 = announce)
- 파일을 수정하면 즉시(수정으로 기존 사본이 무효가 되므로 다시 복제)
- 그 외에는 주기적으로(기본 300초) 아직 복제되지 않은 파일을 훑는다

사용자가 파일 목록에서 오른쪽 클릭 후 "지금 백업 요청"을 선택해 수동으로 알릴 수도
있다. 요청만 하고 전송은 데몬이 수행하므로 화면이 멈추지 않는다.

파일을 수정하면 복제 상태가 "미백업"으로 돌아간다. 청크 식별자는 경로에서 만들어져
수정 전후가 같으므로, 상태를 되돌리지 않으면 홀더가 옛 내용을 들고 있는데도 "백업
완료"로 보이게 된다.

사본에는 조각별 무결성 해시가 붙는다. 복구할 때 받은 조각이 백업 시점과 다르면 그
기기를 건너뛰고 다른 기기에서 다시 받는다. 손상된 조각이 다른 기기로 퍼지지도 않는다.

- 사본은 반드시 다른 기기에 놓인다. 소유자 자신의 기기는 홀더 후보에서 제외한다
  (자기 기기 백업은 무의미).
- 홀더는 내 다른 기기일 수도, 다른 사용자의 기기일 수도 있다(상호 보관).
- 목표 사본 수는 서버 정책으로 내려온다(`min_replicas`, 기본 1 = 원본 외 1부).
- 사본이 부족해지면 유예 기간(기본 24시간) 후 보충한다(heal).

다른 사용자의 기기에 맡긴 조각은 상대가 내용을 볼 수 없다. 조각은 내 열쇠로
암호화된 상태이고, 보관 측은 조각 소유자가 아니면 접근이 거부된다.

```
파일 A ──청크 암호문──▶ [내 다른 기기]  또는  [타 사용자 기기]
                          내용 못 봄(암호문) · 소유자만 fetch 가능
```

주의: 남의 조각을 받아주는 호스팅은 P2P가 활성일 때만 동작한다
(`p2p.enabled`, 기본 false). 내 파일의 백업은 켜져 있어도, 호스팅 참여는
별도 설정이다.

용어: 코드의 `parity_store`는 소거부호(erasure coding)가 아니라 청크 암호문
복제 보관소다. erasure coding은 향후 과제다.

구현: `replication_manager`, `replication_scheduler`, `parity_store`

## 4단: 축출 — 공간이 부족하면 로컬 원본을 비움

로컬 여유 공간이 임계치 아래로 내려가면, 사본이 충분히 확보된 오래된 파일의
로컬 원본을 지우고 "축출됨" 표시만 남긴다. 그 파일을 읽으면 홀더에서 복구해
로컬에 다시 만든 뒤 돌려준다.

- 기본 꺼져 있다(`eviction.enabled`, 기본 false).
- 삭제 직전에 온라인 사본 수를 실측해 목표에 미달하면 보존한다(무손실).
- 축출된 파일은 온라인이어야 읽을 수 있다. 복구 경로가 없으면 에러를 낸다.

```
공간 부족:  파일 A 로컬 원본 삭제 → 표시만 남음
읽을 때:    홀더에서 청크 복구 → 로컬 재생성 → 반환
```

구현: `jbod_manager.evict_cold`, `jbod_manager._materialize_evicted`

## 읽기: 다른 기기의 파일을 열 때

PC-B가 PC-A 소유 파일을 열면 PC-A에서 가져온다. 연결은 3단계로 시도하고 앞이 안
되면 다음으로 내려간다.

1. 직접 TCP — 같은 LAN에 있을 때만. 기기는 LAN 주소를 광고하므로(사용자에게 라우터
   포트포워딩을 요구하지 않는다) 다른 네트워크에서는 성립하지 않는다. 도달 가능성이
   없는 주소면 시도조차 하지 않고 바로 2단계로 간다.
2. 홀펀칭 UDP — 서로 다른 네트워크의 기본 경로. 대부분의 가정용 NAT를 라우터 설정
   없이 통과한다.
3. 서버 릴레이 — 홀펀칭마저 안 되는 symmetric NAT/CGNAT일 때 최후 수단.

같은 계정은 열쇠가 같으므로 받은 암호문을 바로 풀 수 있다.

```
PC-B  ── ① 직접 TCP ──▶  PC-A       (같은 LAN일 때만)
PC-B  ── ② 홀펀칭 UDP ─▶  PC-A       (다른 네트워크의 기본 경로)
PC-B  ── ③ 서버 릴레이 ▶  PC-A       (②도 안 되면, 서버는 암호문만 중계)
```

소유 기기가 오프라인이고 사본도 없으면 목록에는 보이지만 열 수 없다. 상세는
[TRANSPORT.md](./TRANSPORT.md) 참조.

## 수정: 소유권 이전

PC-B에서 PC-A 소유 파일을 고치면 새 내용이 PC-B 로컬에 저장되고 소유권이 PC-B로
넘어온다. 가상 경로는 그대로여서 파일은 여전히 1개로 보인다.

```
고치기 전:  파일 A 실체 = [PC-A]
고친 후:    파일 A 실체 = [PC-B]   (PC-A의 옛것은 정리 대상)
```

PC-A의 옛 물리 파일은 자동 정리되지만 조건이 있다.

- PC-A가 온라인으로 동기화를 돌려야 실행된다(오프라인이면 그때까지 남는다).
- StardustFS가 만든 관리 파일만 지운다(파일명이 32자 hex + `_`로 시작하는 것).
  메타데이터 DB나 사용자가 직접 넣은 파일은 절대 건드리지 않는다.
- 기기 식별자를 모르는 상태에서는 정리를 아예 건너뛴다(전체 삭제 방지).

구현: `jbod_manager._takeover_write`, `jbod_manager.gc_orphan_files`

## 계정이 다를 때

User A와 User B는 서로 다른 계정, 서로 다른 열쇠를 쓴다.

- 각자의 파일은 각자의 기기들 사이에서만 평문으로 오간다.
- 계정이 다르면 파일을 그대로 공유하지 않는다(정책상 금지).
- 예외는 3단의 백업 조각뿐이다. 조각은 암호문이고, 보관 측은 내용을 볼 수 없다.

```
User A 파일  ↔  User A의 기기들       ✅ 평문 그대로 오감
User B 파일  ↔  User B의 기기들       ✅ 평문 그대로 오감
User A 파일  ─▶  User B의 기기         🔒 암호화된 백업 조각만 (내용 못 봄)
User A 파일  ✗   User B와 평문 공유    ❌ 금지
```

## 서버의 역할

서버는 파일 실체를 저장하지 않는다. 서버가 하는 일:

- 로그인 확인
- "누구의 어떤 파일이 어느 기기에 있는지" 메타데이터 보관(내용은 암호문이라 못 봄)
- 백업 조각의 위치·크기·상호 보관 회계 기록(조각 내용은 보관하지 않음)
- 기기끼리 직접 연결이 안 될 때 중계(릴레이)
- 변경이 생기면 다른 기기에 즉시 알림

## 요약 표

| 상황 | 파일 실체 위치 | 서버 |
| --- | --- | --- |
| PC-A가 만든 파일 | PC-A 로컬 | 위치 메타데이터만(암호문) |
| PC-A 로컬이 만석 | 내 다른 온라인 기기(스필오버) | 위치 메타데이터만 |
| 백업 사본 | 다른 기기에 암호문 청크(기본 켜짐, 저장·수정 시 즉시) | 조각 위치·회계만 |
| 공간 부족 시 축출 | 로컬 원본 비움, 사본에서 복구(기본 꺼짐) | 조각 위치만 |
| PC-B가 그 파일 읽기 | 소유 기기에서 가져옴(같은 LAN이면 직접 TCP, 아니면 홀펀칭 UDP→릴레이) | 필요 시 중계 |
| PC-B가 그 파일 수정 | PC-B로 이전, PC-A 옛 파일은 온라인 시 정리 | 변경 알림 |
| 다른 계정 파일 | 각자 기기에만 | 평문 공유 금지, 암호 백업 조각만 |

## 가용성에 대한 참고

파일의 완전본은 소유 기기에 있고, 그 기기가 오프라인이면 사본이 있어야 읽을 수
있다. 사본도 홀더가 온라인일 때만 쓸 수 있다. 따라서 실효 가용성은 "내 기기 또는
홀더 중 최소 한 대가 켜져 있을 확률"에 좌우된다. 상시 가동 홀더와 등급별 사본 수
정책은 ROADMAP의 MVP4(서비스 플랫폼) 과제다.
