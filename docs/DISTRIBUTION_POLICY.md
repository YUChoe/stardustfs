# StardustFS 파일 저장 위치 정책

파일이 실제로 어디에 저장되는지를 예시로 설명한다. 서버는 어떤 경우에도 파일
내용을 저장하지 않는다(zero-knowledge).

## 저장 단위는 조각(청크)이다

파일은 저장하는 순간부터 조각으로 나뉜다. 4 MiB씩 자르고 조각마다 따로 암호화해
보관한다. 통짜 파일 하나를 어딘가에 두는 방식이 아니다.

조각마다 독립적으로 암호화하므로 조각 하나만 있어도 그 부분을 풀 수 있고, 조각마다
보관처를 따로 정할 수 있다. 그래서 아래 4단은 모두 "파일 단위"가 아니라 "조각 단위"로
일어난다. 한 파일의 조각이 여러 소스, 여러 기기에 흩어져 있어도 읽을 때 각자의 보관처
에서 모아 온다.

저장·전송·백업이 모두 같은 조각 표현을 쓴다. 백업할 때 다시 자르거나 다시 암호화하지
않고 저장된 조각을 그대로 보낸다.

기존에 통짜로 저장된 파일도 계속 읽힌다. 그 파일을 수정하거나 마이그레이션 대상으로
고르면 조각 표현으로 전환된다(전환 중 실패해도 원본을 잃지 않는다).

```
파일 A (10 MiB) ─▶ 조각0(4MiB) 조각1(4MiB) 조각2(2MiB)   각각 따로 암호화
                     └ PC-A      └ PC-A      └ PC-B(만석 시)
```

핵심: 조각(암호문)의 위치는 4단으로 결정된다.

1. 기본은 파일을 만든 기기의 로컬 스토리지
2. 로컬이 차면 내 다른 온라인 기기로 넘김(스필오버) — 조각 단위
3. 백업 사본은 다른 기기에 조각으로 복제
4. 공간이 부족하면 로컬 원본을 비우고, 읽을 때 사본에서 복구(축출, 기본 꺼짐)

다른 기기는 "어느 조각이 어디에 있는지"만 안다(메타데이터의 조각 목록). 필요할 때
가져온다.

## 1단: 기본 배치 — 만든 기기

PC-A에서 파일 A를 만들면 조각들이 PC-A의 로컬 스토리지에 저장된다. 로컬 소스가
여러 개면 여유 공간이 가장 많은 소스를 고른다(원격 소스는 후보에서 제외). 파일 하나가
한 소스에 다 들어가면 그 소스에 모아 두고, 부족하면 조각마다 따로 고른다.

- PC-B에는 "파일 A의 조각들이 어디에 있다"는 메타데이터만 서버를 통해 전달된다.
- PC-B 화면에는 파일 A가 보이지만 실체는 없다.

```
파일 A 조각:  [PC-A ✅]   [PC-B ❌ 목록만 보임]
```

조각은 소스 안에서 해시 앞 두 자리로 나눈 하위 디렉터리에 흩어 둔다. 한 디렉터리에
파일이 쌓이면 FAT 이미지 쓰기가 급격히 느려지기 때문이다(실측 근거는
`.kiro/specs/chunk-native-storage/design.md`).

구현: `storage_pool.write_file` → `_place_chunks` → `select_source`(로컬 활성 소스 중
여유 최대)

## 2단: 스필오버 — 로컬이 차면 내 다른 기기 (조각 단위)

조각을 놓을 로컬 공간이 없으면 그 조각만 내 계정의 다른 온라인 기기로 보내 저장한다.
파일 전체가 넘어가는 것이 아니라 넘치는 조각만 넘어간다.

- 즉 PC-A에서 만든 파일의 일부 조각이 PC-B에 저장될 수 있다. 앞쪽 조각은 PC-A에,
  뒤쪽 조각은 PC-B에 있는 상태가 정상이다.
- 조각이 원격에 놓여도 파일 레코드의 소유자는 만든 기기(PC-A)로 남는다. 보관처는
  조각마다 따로 기록한다. 소유권까지 넘기면 그 파일을 지우거나 고칠 주체가 사라져
  삭제가 실체를 정리하지 못한다.
- 도달 가능한 온라인 기기가 없으면 저장하지 않고 용량 부족 에러를 낸다(무손실,
  조용히 건너뛰지 않는다). 이미 기록한 조각은 정리한다.
- 기존 파일 덮어쓰기는 지금 있는 소스를 우선한다(여유가 있으면 그 소스에 새 조각을
  쓴다). 덮어쓰기가 파일을 다른 소스로 옮기지 않게 해 배치를 안정적으로 유지한다.

```
로컬 만석:  PC-A ──조각2 암호문──▶ [PC-B에 보관]
            파일 소유 = PC-A 유지 · 조각2 보관처 = PC-B
도달 불가:  저장 실패 (InsufficientStorageError), 기록한 조각 정리
```

구현: `storage_pool._place_one_chunk`, `_push_chunk_to_remote`

## 3단: 백업 사본 — 다른 기기에 암호문 조각으로

데몬이 저장된 조각을 그대로 다른 기기에 복제한다. 기본으로 켜져 있다
(`replication.enabled`, 기본 true).

저장 단위가 이미 조각이므로 백업할 때 다시 자르거나 다시 암호화하지 않는다. 저장된
조각 바이트를 그대로 보내고, 복구할 때도 받은 조각을 그대로 되돌려 놓는다. 그래서 복구
후에도 조각의 무결성 해시가 그대로 유효하다. (통짜로 저장된 옛 파일은 예전처럼 고정
크기로 나눠 복제한다.)

복제가 시작되는 시점은 세 가지다.

- 파일을 저장하면 즉시(데몬이 전송을 마친 직후 스스로 알림 = announce)
- 파일을 수정하면 즉시(수정으로 기존 사본이 무효가 되므로 다시 복제)
- 그 외에는 주기적으로(기본 300초) 아직 복제되지 않은 파일을 훑는다

사용자가 파일 목록에서 오른쪽 클릭 후 "지금 백업 요청"을 선택해 수동으로 알릴 수도
있다. 요청만 하고 전송은 데몬이 수행하므로 화면이 멈추지 않는다.

파일을 수정하면 복제 상태가 "미백업"으로 돌아간다. 청크 식별자는 경로에서 만들어져
수정 전후가 같으므로, 상태를 되돌리지 않으면 홀더가 옛 내용을 들고 있는데도 "백업
완료"로 보이게 된다.

사본에는 조각별 무결성 해시가 붙는다. 복구할 때 받은 조각이 백업 시점과 다르면 그
기기를 건너뛰고 다른 기기에서 다시 받는다. 손상된 조각이 다른 기기로 퍼지지도 않는다.

- 사본은 반드시 다른 기기에 놓인다. 소유자 자신의 기기는 홀더 후보에서 제외한다
  (자기 기기 백업은 무의미).
- 홀더는 내 다른 기기일 수도, 다른 사용자의 기기일 수도 있다(상호 보관).
- 목표 사본 수는 서버 정책으로 내려온다(`min_replicas`, 기본 1 = 원본 외 1부).
- 사본이 부족해지면 유예 기간(기본 24시간) 후 보충한다(heal).

다른 사용자의 기기에 맡긴 조각은 상대가 내용을 볼 수 없다. 조각은 내 열쇠로
암호화된 상태이고, 보관 측은 조각 소유자가 아니면 접근이 거부된다.

```
파일 A ──청크 암호문──▶ [내 다른 기기]  또는  [타 사용자 기기]
                          내용 못 봄(암호문) · 소유자만 fetch 가능
```

기기 간 통신(P2P)과 남의 조각을 받아주는 호스팅은 둘 다 기본으로 켜져 있고, 서버가
정책으로 내려 제어한다(프로비저닝). 사용자가 직접 설정을 만질 일은 없다.

- `p2p_enabled` — 피어 서빙 자체. 끄면 내 다른 기기의 파일도 가져올 수 없다.
- `hosting_enabled` — 다른 계정의 조각을 맡아 주는 참여. 끄면 내 파일 백업은 그대로
  동작하고 남의 조각만 받지 않는다.

엔터프라이즈처럼 자체 풀만 쓰는 경우는 보통 P2P는 켜고 호스팅만 끈다. 정책이 호스팅을
금지하면 보관 요청은 조용히 무시되지 않고 규격 거부(503)로 응답한다.

용어: 코드의 `parity_store`는 소거부호(erasure coding)가 아니라 청크 암호문
복제 보관소다. erasure coding은 향후 과제다.

구현: `replication_manager`, `replication_scheduler`, `parity_store`

## 4단: 축출 — 공간이 부족하면 로컬 원본을 비움

로컬 여유 공간이 임계치 아래로 내려가면, 사본이 충분히 확보된 오래된 파일의
로컬 원본을 지우고 "축출됨" 표시만 남긴다. 그 파일을 읽으면 홀더에서 복구해
로컬에 다시 만든 뒤 돌려준다.

- 기본 꺼져 있다(`eviction.enabled`, 기본 false).
- 삭제 직전에 온라인 사본 수를 실측해 목표에 미달하면 보존한다(무손실).
- 축출된 파일은 온라인이어야 읽을 수 있다. 복구 경로가 없으면 에러를 낸다.

```
공간 부족:  파일 A 로컬 원본 삭제 → 표시만 남음
읽을 때:    홀더에서 청크 복구 → 로컬 재생성 → 반환
```

구현: `storage_pool.evict_cold`, `storage_pool._materialize_evicted`

## 읽기: 다른 기기의 파일을 열 때

읽기는 조각 목록을 보고 조각마다 제 보관처에서 가져온 뒤 순서대로 합친다. 파일 단위
소유자가 아니라 조각의 보관 기기를 따라간다. 조각이 로컬과 원격에 섞여 있으면 로컬은
바로 읽고 원격만 전송한다.

파일의 일부만 필요하면 그 범위를 덮는 조각만 가져온다. 앞부분 몇 바이트를 보려고 전체를
받지 않는다. 받은 조각은 저장 시점 해시와 대조하고, 어긋나거나 없으면 어느 조각인지
밝히며 실패한다(조용히 넘어가지 않는다).

원격 조각을 가져올 때 연결은 3단계로 시도하고 앞이 안 되면 다음으로 내려간다.

1. 직접 TCP — 같은 LAN에 있을 때만. 기기는 LAN 주소를 광고하므로(사용자에게 라우터
   포트포워딩을 요구하지 않는다) 다른 네트워크에서는 성립하지 않는다. 도달 가능성이
   없는 주소면 시도조차 하지 않고 바로 2단계로 간다.
2. 홀펀칭 UDP — 서로 다른 네트워크의 기본 경로. 대부분의 가정용 NAT를 라우터 설정
   없이 통과한다.
3. 서버 릴레이 — 홀펀칭마저 안 되는 symmetric NAT/CGNAT일 때 최후 수단.

전송되는 것은 저장된 암호문 그대로다. 같은 계정은 열쇠가 같으므로 받은 뒤 로컬에서
풀어 사용한다. 어떤 경로에서도 평문이 네트워크에 나가지 않는다.

```
PC-B  ── ① 직접 TCP ──▶  PC-A       (같은 LAN일 때만)
PC-B  ── ② 홀펀칭 UDP ─▶  PC-A       (다른 네트워크의 기본 경로)
PC-B  ── ③ 서버 릴레이 ▶  PC-A       (②도 안 되면, 서버는 암호문만 중계)
```

조각을 보관한 기기가 오프라인이고 사본도 없으면 목록에는 보이지만 열 수 없다. 조각이
여러 기기에 흩어져 있으면 그 기기들이 모두 도달 가능해야 파일 전체를 읽을 수 있다.
상세는 [TRANSPORT.md](./TRANSPORT.md) 참조.

구현: `storage_pool.read_file`, `read_range`, `_read_chunk_bytes`

## 수정: 소유권 이전

PC-B에서 PC-A 소유 파일을 고치면 새 내용이 PC-B 로컬에 저장되고 소유권이 PC-B로
넘어온다. 가상 경로는 그대로여서 파일은 여전히 1개로 보인다.

```
고치기 전:  파일 A 실체 = [PC-A]
고친 후:    파일 A 실체 = [PC-B]   (PC-A의 옛것은 정리 대상)
```

PC-A의 옛 물리 파일은 자동 정리되지만 조건이 있다.

- PC-A가 온라인으로 동기화를 돌려야 실행된다(오프라인이면 그때까지 남는다).
- StardustFS가 만든 관리 파일만 지운다(파일명이 32자 hex + `_`로 시작하는 것).
  메타데이터 DB나 사용자가 직접 넣은 파일은 절대 건드리지 않는다.
- 기기 식별자를 모르는 상태에서는 정리를 아예 건너뛴다(전체 삭제 방지).

구현: `storage_pool._takeover_write`, `storage_pool.gc_orphan_files`

## 계정이 다를 때

평문은 어떤 경로로도 네트워크에 나가지 않는다. 내 기기끼리든 다른 계정 기기든,
오가는 것은 항상 암호문이다. 그래서 보관 측 관점에서 모든 기기는 구조적으로 같다 —
전부 "읽을 수 없는 암호문 조각을 맡아 두는 곳"이다.

저장 단위가 조각이 되면서 이 동일성이 서술이 아니라 실제 구조가 됐다. 내 다른 기기에
스필오버로 맡기는 것도 조각이고, 다른 계정 기기에 백업으로 맡기는 것도 조각이다. 주고
받는 것도, 보관하는 것도 같은 표현이다.

차이는 두 가지뿐이다.

- 열쇠: 내 기기는 같은 열쇠를 가지므로 받은 암호문을 풀 수 있다. 다른 계정 기기는
  열쇠가 없어 무엇을 보관하는지도 알 수 없다.
- 인가: 내 파일 전체를 요청할 수 있는 것은 내 기기뿐이다. 다른 계정 기기는 자신이
  맡은 백업 조각만 주고받을 수 있고, 그 조각도 소유자 본인 요청일 때만 응한다.

```
암호문 전송        내 기기 ↔ 내 기기        🔑 열쇠 있음 → 받아서 풀 수 있다
암호문 전송        내 기기 → 남의 기기      🔒 열쇠 없음 → 보관만, 내용 모름
파일 전체 요청     내 기기만                ✅ 같은 계정만 인가
백업 조각 요청     조각 소유자만            ✅ 보관 측이 소유자 확인 후 응답
```

저장 위치를 고르는 우선순위(내 기기 먼저, 그다음 다른 계정 기기 등)는 서비스 정책의
문제이고, 데이터 취급 방식은 어느 쪽이든 동일하다.

## 서버의 역할

서버는 파일 실체를 저장하지 않는다. 서버가 하는 일:

- 로그인 확인
- "누구의 어떤 파일이 어느 기기에 있는지" 메타데이터 보관(내용은 암호문이라 못 봄)
- 백업 조각의 위치·크기·상호 보관 회계 기록(조각 내용은 보관하지 않음)
- 기기끼리 직접 연결이 안 될 때 중계(릴레이)
- 변경이 생기면 다른 기기에 즉시 알림

## 요약 표

| 상황 | 조각(암호문) 위치 | 서버 |
| --- | --- | --- |
| PC-A가 만든 파일 | 조각들이 PC-A 로컬 | 조각 목록 메타데이터만(암호문) |
| PC-A 로컬이 만석 | 넘치는 조각만 내 다른 온라인 기기로(파일 소유는 PC-A 유지) | 조각 목록만 |
| 백업 사본 | 저장된 조각을 재분할 없이 다른 기기로(기본 켜짐, 저장·수정 시 즉시) | 조각 위치·회계만 |
| 공간 부족 시 축출 | 로컬 조각 비움, 사본에서 복구(기본 꺼짐) | 조각 위치만 |
| PC-B가 그 파일 읽기 | 조각마다 제 보관처에서 가져와 합친 뒤 로컬에서 복호화(같은 LAN이면 직접 TCP, 아니면 홀펀칭 UDP→릴레이) | 필요 시 중계 |
| 파일 일부만 읽기 | 그 범위를 덮는 조각만 가져옴 | 필요 시 중계 |
| PC-B가 그 파일 수정 | PC-B로 이전, PC-A 옛 조각은 온라인 시 정리 | 변경 알림 |
| 다른 계정 기기 | 백업 조각만 보관(열쇠 없음, 소유자 요청만 응답) | 조각 위치·회계만 |
| 통짜로 저장된 옛 파일 | 그대로 읽힘, 수정·선택 시 조각으로 전환(무손실) | 변경 알림 |

## 가용성에 대한 참고

파일을 읽으려면 모든 조각을 확보해야 한다. 조각이 한 기기에 모여 있으면 그 기기 또는
사본 홀더 중 한 대가 켜져 있으면 되지만, 스필오버로 조각이 여러 기기에 흩어지면 각
조각마다 보관 기기 또는 그 조각의 홀더가 도달 가능해야 한다. 조각이 흩어질수록 필요한
"켜져 있어야 하는 대상"이 늘어난다는 뜻이다.

이것이 백업(3단)이 기본으로 켜져 있는 이유다. 사본이 있으면 조각 하나를 여러 곳에서
받을 수 있어 특정 기기의 오프라인이 파일 전체를 막지 않는다.

상시 가동 홀더와 등급별 사본 수 정책은 ROADMAP의 MVP4(서비스 플랫폼) 과제다.
